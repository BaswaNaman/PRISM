# PRISM — Product Intelligence & Commerce Content Engine

> Multi-source ingestion (URL / PDF / text) → AI extraction with verbatim evidence →
> deterministic validation → **trust-gated** generation of the five Unilog commerce
> description formats, scored against the content guidelines.

Built for the UniHack / Unilog Product Intelligence challenge.

---

## What this system actually does

PRISM has two halves, and a gate between them that is the point of the whole design.

**Half one — get the data, and know how much to trust it.** A product page, a PDF
datasheet or a pasted blurb comes in. Text is cleaned, the main content region is
isolated, spec tables are flattened to `Label: Value` lines, and an AI chain
(Gemini → Claude → deterministic regex) extracts attributes. Every extracted value
carries a verbatim `source_snippet`. That snippet is then checked back against the
source text — if the quote is not in the source, the value is marked
`flagged_ungrounded`, because a confident-sounding value with invented evidence is
the most expensive failure mode in catalogue work.

**Half two — turn the trusted data into sellable content.** Attributes are
normalised (decimal ↔ fraction in 64ths, UOM abbreviations with the mandatory
number-unit space), brands are canonicalised, item type is classified, values are
checked against the LOV controlled vocabulary, and five description formats are
generated to their character limits.

**The gate.** Only values that survived verification reach a description. An
ungrounded value, an AI-inferred value, or a value below the confidence threshold
is *withheld*, with a reason attached. This is deliberate: an invented
specification scores zero against ground truth, so publishing nothing beats
publishing a guess. Every withheld field stays visible in the UI and the API — the
system never silently drops data.

## Quick start

```bash
cd claude                      # the project root — everything below runs from here
pip install -r requirements.txt
cp .env.example .env           # then add your GEMINI_API_KEY / ANTHROPIC_API_KEY
python run.py                  # http://127.0.0.1:8000
```

No API key? The extractor falls back to its deterministic regex layer, so the app
still runs end to end — values simply arrive with lower confidence.

The compliance half needs no keys and no server:

```bash
python run_unilog_pipeline.py --demo          # five formats + classifier + LOV + trust gate
python run_unilog_pipeline.py --xlsx data/Faucets_Data.xlsx   # run over a real workbook
python test_url_accuracy.py                   # 26 assertions over the extraction guards
python test_unilog_modules.py                 # unit tests for the compliance modules
```

## The five description formats

Generated by `unilog/descriptions.py`, each to its own limit, each reported
pass/fail:

| Format | Limit | Shape |
|---|---|---|
| Invoice Description | ≤ 40 chars, upper-case | Abbreviated, ERP-safe: `CPLG 3/8 IN BRS 150 THD` |
| Mobile Description | 60–80 chars | Brand + type + the two most identifying specs |
| Product Title / Short Desc | ≤ 200 chars | Brand, MPN, item type, key attributes |
| Long Description | ≤ 1000 chars | Full attribute prose, spec-complete |
| Web / Online Description | 120–1500 chars | Readable sentences for a product page |

The limits live in one place — `INVOICE_MAX`, `MOBILE_MIN/MAX`, `TITLE_MAX`,
`LONG_DESC_MAX`, `WEB_MIN/MAX` at the top of `unilog/descriptions.py` — so if the
graded spec differs, change them there and every compliance number follows.

The web format drops whole sentences from the tail rather than truncating
mid-word, and deliberately adds no adjectives or benefit claims — every clause
traces to an attribute that passed the gate.

## The trust gate in detail (`unilog/bridge.py`)

An attribute is admitted to a description only if all of these hold:

- status is `verified` or `flagged_low_confidence` — never `flagged_ungrounded`,
  `flagged_validation_error` or `missing`
- confidence ≥ 0.65
- it was sourced, not inferred — unless you explicitly pass
  `include_enriched=true`, which is off by default and labelled when on

Anything refused comes back in `trust_report.withheld` with a human-readable
reason, e.g. *"evidence could not be located in the source (possible
hallucination)"* or *"confidence 0.55 below the 0.65 publication threshold"*.

## Sourcing policy (`app/sourcing.py`)

The guidelines require manufacturer sources. PRISM enforces that **before** the
HTTP request is made, so a rejected source is never fetched and its text can
never leak into a record. Domains are classified as `manufacturer`,
`marketplace`, `distributor`, `encyclopedic`, `community` or `unknown` — an
unrecognised domain is never optimistically called a manufacturer; it is
permitted but flagged for review.

| Policy | Behaviour |
|---|---|
| `manufacturer_only` *(default)* | Marketplaces, distributors, encyclopedias and forums rejected |
| `allow_distributors` | Distributors permitted, marketplaces still rejected |
| `warn_only` | Nothing blocked; everything non-manufacturer flagged |
| `allow_all` | Gate disabled |

Set with `PRISM_SOURCING_POLICY` in `.env`. For a graded or audited run, copy
`data/approved_domains.txt.example` to `data/approved_domains.txt` — while that
file exists it overrides the category rules entirely and only listed domains may
be fetched.

## Item-type classification (`unilog/classify.py`)

Terse trade strings are expanded first (`CPLG` → coupling, `BRS` → brass,
`FCT` → faucet, `THD` → threaded), then scored against candidate types by
IDF-weighted whole-token overlap. When a LOV workbook is loaded, the candidate
set *is* the LOV taxonomy, so a classification also yields a classpath and the
attribute set that classpath permits. Without a workbook it falls back to a
built-in ~75-type taxonomy weighted toward fittings and faucets. Results below
the score threshold, or too close to the runner-up, are marked `needs_review`
rather than guessed. Without a workbook it falls back to a built-in 79-type
taxonomy weighted toward fittings and faucets.

## API endpoints

| Endpoint | Purpose |
|---|---|
| `POST /api/enrich` | Ingest + extract + validate one product |
| `GET /api/products`, `GET /api/products/{id}` | Stored catalogue |
| `GET /api/stats` | Verification / flag counts |
| `GET /api/unilog/report?limit=100` | **Full compliance report**: char-limit %, LOV %, classification rate, trust-gate pass rate, dedup, per-product descriptions |
| `GET /api/unilog/product/{id}` | The five formats + trust audit for one product |
| `GET /api/sourcing/policy` | What the gate is enforcing and how to change it |
| `POST /api/sourcing/check` | Classify a URL *without* fetching it |

The UI's fourth tab, **Commerce Output & Compliance**, is a front end over
`/api/unilog/report`: four KPI tiles, the report context, a live sourcing-policy
checker, and every product's five descriptions with pass/fail badges and the list
of attributes the trust gate withheld.

## Adding the supplied workbooks

Most of the dataset-driven machinery is built but idle until the challenge
workbooks are present. Drop them in `data/` with these names and the LOV
registry, brand canonicaliser, evaluator and classifier taxonomy all light up
automatically — no code changes:

```
data/Unicat_Lov_v1_0_Updated_With_Remarks.xlsx     # 161k LOV rows
data/FAUCETS_LOV.xlsx  |  data/Fittings_LOV.xlsx   # category LOVs
data/Manufacturer_Brand.xlsx                       # 27k brand records
data/Faucets_Data.xlsx |  data/Fittings_Data.xlsx  # raw input rows
data/Ground_Truth_200.xlsx                         # scoring set
```

**Until then, LOV compliance is reported as `UNAVAILABLE`, not as 100%.** A
compliance percentage computed against an empty vocabulary is not a score, and
quoting one would be the most misleading number in the report. The API returns an
`unavailable_reason` explaining exactly why the number is withheld, and the UI
shows that reason verbatim.

## Honest status

**Working end to end:** URL / PDF / text ingestion, spec-table recovery, the AI
chain with snippet grounding, deterministic validation, the sourcing gate,
item-type classification, attribute recovery from terse strings, fraction and UOM
normalisation, all five description formats with char-limit scoring, the trust
gate with per-field refusal reasons, dedup, the API and the UI.

**Built but unproven without the workbooks:** LOV validation — the validator is
invoked on every run, it simply has nothing to validate against yet — plus brand
canonicalisation at 27k scale and field-level accuracy against the 200-item
ground truth.

**Known structural limitation:** the extractor's fixed attribute set is electrical
(voltage, current, IP rating, connector type, temperature range), while the
ground-truth categories are faucets, fittings and appliances. The generic path —
`attrparse.py` plus the LOV attribute set for a classpath — handles those
categories, but the eleven typed fields do not, so raw extraction scores on
plumbing items will be lower than the trust layer's quality suggests. That is a
coverage gap rather than a correctness one, and it is the first thing to widen if
you extend the project.

`README_CHANGES.md` documents every change made, with reasoning, and lists what
remains.
